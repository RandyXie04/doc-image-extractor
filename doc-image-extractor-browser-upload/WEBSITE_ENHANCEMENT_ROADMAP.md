# 文件圖片提取器：網站完善路線圖

## 一、目前版本評估

目前版本已經具備拖曳上傳 PDF／DOCX、多檔案處理、PDF 內嵌圖片轉 PNG、DOCX 原始媒體提取、圖片預覽、ZIP 下載，以及共用密碼登入。程式也已設定單次檔案數與總容量限制，並透過 Streamlit Cloud Secrets 讀取 `APP_PASSWORD`，不把正式密碼寫入 GitHub。

本次 P0 更新已將認證設定統一為 `APP_PASSWORD`，並移除舊版密碼雜湊流程與產生器，避免部署文件與實際程式不一致。

公開部署後，最需要優先補強的不是視覺效果，而是**資料生命週期、公開服務的濫用防護、密碼管理與錯誤處理**。Streamlit 官方建議將敏感資料放在儲存庫外的 Secrets 或環境變數，並指出 Community Cloud 需要在平台的 Secrets 管理介面另外設定秘密值。[1]

## 三、最應立即處理的事項

### 1. 統一 Secrets 設定名稱

目前程式已支援直接從 Cloud Secrets 讀取：

```toml
APP_PASSWORD = "你的長密碼"
```

這項 P0 已完成：部署設定統一使用 `APP_PASSWORD`。實際密碼不應提交到 GitHub；Streamlit 官方也明確建議不要把未加密秘密放入 Git 儲存庫。[1]

共用密碼建議至少 16 字元，並避免使用姓名、生日、網站名稱或其他可猜測內容。網站公開後，若懷疑密碼外洩，應直接在 Streamlit Cloud Secrets 中更換密碼並重新啟動 App。

### 2. 加強暫存資料清理

目前提取結果會先寫入執行環境的暫存資料夾，再建立 ZIP。建議在 ZIP bytes 建立完成後，立即刪除原始上傳檔、提取圖片與中間資料夾；下載按鈕可以使用記憶體中的 ZIP bytes，不必讓圖片長時間留在磁碟中。

同時應在 PDF 開啟失敗、DOCX 讀取失敗、ZIP 建立失敗與使用者重新開始處理時執行清理。這不能保證雲端平台的所有底層暫存都立即消失，但能避免應用程式自行留下不必要的檔案。

### 3. 增加不可信文件的資源上限

公開上傳服務必須把 PDF 和 DOCX 視為不可信輸入。除了目前的檔案數與大小限制，建議增加以下上限：PDF 最大頁數、每頁最多處理的圖片數、單張圖片最大寬高、DOCX ZIP 解壓後總大小、單一媒體檔大小與全部輸出檔案總大小。

DOCX 是 ZIP 容器，不能只檢查上傳檔案的壓縮大小；需要在讀取 `word/media/` 之前檢查每個 ZIP member 的 `file_size` 與累計解壓大小，避免壓縮炸彈。PDF 也應限制頁數及圖片數，並在達到上限時回傳清楚警告，而不是繼續消耗資源。

## 四、使用體驗升級

### 1. 兩種 PDF 模式

目前 PDF 功能是「提取 PDF 內嵌圖片」，這對排版檔、掃描檔與圖文混排文件很有用，但它不會把文字或向量圖形變成圖片。建議加入下拉選單：

| 模式 | 適用情境 | 輸出 |
|---|---|---|
| 提取內嵌圖片 | 需要取得原始插圖、照片或掃描物件 | 依內嵌圖片輸出 PNG |
| 整頁渲染 | 需要保留頁面完整外觀、文字與向量圖形 | 依頁面輸出高解析度 PNG |

整頁渲染應提供 DPI 或倍率選項，並設定最大頁數與最大輸出像素，避免使用者上傳大型 PDF 後產生數 GB 圖片。

### 2. 更精細的下載方式

除了「下載全部圖片 ZIP」，可加入每個來源文件的下載按鈕、單張圖片下載，以及多選圖片後下載。結果表可顯示檔名、來源頁碼、寬度、高度、格式與檔案大小，使用者就能在下載前快速判斷內容。

### 3. 重複圖片與檔名管理

PDF 可能在多頁重複引用同一個 XREF，DOCX 也可能存在內容相同但檔名不同的圖片。可對輸出 bytes 計算 SHA-256，提供「保留全部」與「移除完全相同圖片」選項。這能大幅減少書籍型 PDF 的重複輸出。

### 4. 進度與錯誤報告

對大型文件，進度列應分成「目前文件／總文件」與「目前頁面／總頁面」。處理完成後可提供一個簡短報告，列出成功張數、略過張數、失敗張數、警告原因及輸出總容量；若使用者需要，也可以把報告一起放進 ZIP。

## 五、效能與維運

Streamlit Community Cloud 應視為受限制的雲端執行環境，而不是無限資源的檔案伺服器。建議避免把大型影像長時間放在 `st.session_state`，並將「上傳、提取、打包、清理」控制在單次工作流程內。若未來需要多人同時處理大型文件，應考慮把工作佇列與檔案儲存拆到具備背景工作能力的服務。

建議加入以下維運能力：

1. 對每次工作產生不含文件內容的工作編號，錯誤訊息只記錄類型、大小與處理階段，不記錄文件文字或圖片內容。
2. 對處理時間、提取數量、失敗類型與輸出大小做匿名統計，但必須先確認隱私需求；不應把原始檔案或檔案名稱送到外部分析服務。
3. 提供管理員可手動旋轉共用密碼的流程，並保留一份不含秘密值的部署檢查表。
4. 固定釘選主要相依套件版本，避免 Streamlit、PyMuPDF 或 Pillow 更新後造成部署行為突然改變。
5. 建立最小化測試樣本，涵蓋 RGB、CMYK、DeviceN、透明 PNG、SVG、空白文件、損壞 PDF、損壞 DOCX 與壓縮炸彈防護。

## 六、公開服務的存取策略

共用密碼適合少量、可信任的分享對象，但它不是個別身份管理。任何拿到密碼的人都能使用服務，而且應用層的單一工作階段鎖定不能完全取代 IP 層級的速率限制或 WAF。

如果網站會給較多人或不熟悉的使用者使用，建議改成下列其中一種：

| 方案 | 優點 | 代價 |
|---|---|---|
| Streamlit Cloud 私有 App + 指定 viewer | 不需要在 App 內共享密碼，存取者可個別管理 | 使用者需要登入 Streamlit／GitHub，且分享管理較麻煩 |
| Google／Microsoft OIDC | 可限制 Email、撤銷個別使用者、保留登入紀錄 | 需要建立 OAuth／OIDC 設定與管理 redirect URI |
| Cloudflare Access | 可用 Email OTP、網域、群組與政策限制 | 需要 Cloudflare 網域與額外部署設定 |
| 共用密碼 | 最容易部署 | 無法識別個人，密碼外洩後需整體更換 |

Streamlit 官方文件說明，Community Cloud 可以在 App settings → Sharing 設定公開或私有，私有 App 也可以加入指定 viewer。[2] 因此，如果資料敏感度提高，優先考慮把 App 設為私有，而不是只依賴共用密碼。

## 七、我建議的實作順序

第一階段先處理三件事：統一 `APP_PASSWORD` 設定、完成處理後暫存清理、加入 DOCX／PDF 資源上限。這三項直接影響公開服務的安全與穩定性。

第二階段加入 PDF 整頁渲染模式、單檔下載、重複圖片偵測與處理報告。這些功能能明顯提升工具的實用性，但不必先改變部署架構。

第三階段再將共用密碼升級為 OIDC 或指定 viewer，並視使用量決定是否加入資料庫、背景工作佇列、物件儲存與管理員介面。當檔案處理量或使用者數增加時，這會比繼續堆疊 Streamlit 介面更重要。
